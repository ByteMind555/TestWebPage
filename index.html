Project Overview

The Order Management Platform is a comprehensive system designed to handle customer orders with an event-driven architecture. It provides robust order management capabilities with automatic event processing, retry mechanisms, and multi-channel notification delivery (Email and SMS).

Order Management

Complete CRUD operations for managing customer orders and items with RESTful APIs

Event Processing

Automated event handling with scheduler-based processing every 5 seconds

Retry Mechanism

Intelligent retry logic with up to 5 attempts and 30-second intervals

Notification Service

Multi-channel notifications via Email and SMS based on customer preferences

System Architecture

The platform follows a microservices architecture with two main services: the Order API and the Notification Service, connected via Kafka for asynchronous event processing.

Figure 1: System Architecture Overview

Architecture Components

  • order-api (Spring Boot): Main API service handling order operations, event scheduling, and Kafka publishing
  • H2 Database: In-memory transactional datastore for orders, customers, and events
  • Order Event Scheduler: Polls every 5 seconds for pending events and triggers processing
  • Kafka Broker: Message broker with "order-notification-topic" for event distribution
  • notification-service (Spring Boot): Consumes events and routes notifications to Email/SMS gateways
  • External Gateways: Email Gateway and SMS Gateway for message delivery to end users

Database Schema

The system uses five main entities to manage orders, customers, items, and events with proper relationship mapping.

Order Processing Flow

Create and Update Flow

Figure 5: Order Creation and Update Workflow

Flow Steps:

  1. Persist Order: Actor creates order via POST to order-api, data saved to H2 database
  2. Event Scheduling: OrderEvent Scheduler polls database every 5 seconds for state changes
  3. Event Publishing: Create/update state change events pushed to Kafka topic
  4. Event Consumption: Notification-service listens to events from Kafka
  5. Notification Routing: Events routed to Email or SMS based on customer preference

Event Processing & Retry Mechanism

The system implements a robust retry mechanism to handle transient failures during event processing.

Figure 7: CustomerOrderEventProcessor - Processing & Retry Flow

Processing Logic

Success Path:

  1. Event status set to PROCESSING with nextRetryAt = now + 30s
  2. Publisher attempts to publish event to Kafka
  3. On success: status = SENT, retryCount++, nextRetryAt = null

Failure Path:

  1. Publisher throws exception
  2. RetryCount incremented, timeUpdated = now
  3. If retryCount < 5: status = RETRY
  4. If retryCount >= 5: status = FAILED, nextRetryAt = null

Retry Configuration

Parameter Value Description
MAX_RETRY 5 Maximum number of retry attempts
RETRY_DELAY 30 seconds Delay between retry attempts
Polling Frequency 5 seconds Scheduler checks for pending events

Technical Highlights

Design Patterns & Best Practices

  • Repository Pattern: Clean data access abstraction using Spring Data JPA
  • Event Sourcing: All order state changes captured as events
  • Retry Pattern: Exponential backoff with configurable retry limits
  • Separation of Concerns: Clear boundaries between API, service, and data layers
  • Transactional Safety: ACID compliance with saveAndFlush operations

Technology Stack

  • Spring Boot for application framework and dependency injection
  • Spring Data JPA for ORM and database operations
  • Kafka for asynchronous event-driven messaging
  • H2 Database for in-memory data storage
  • Swagger/OpenAPI for API documentation
  • JUnit 5 & Mockito for comprehensive unit testing

Testing Strategy

  • Unit tests covering all business logic paths
  • Mock-based testing for external dependencies
  • Verification of retry logic and state transitions
  • Edge case handling (max retries, null values, concurrent updates)
